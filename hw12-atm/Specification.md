# Техническое задание
## Проект: Разработка базового модуля (ядра) процессорабанкомата (ATM Core)
### 1. Общее описание системы
Необходимо разработать объектно-ориентированную библиотеку/модуль, моделирующий логику работы устройства хранения и 
выдачи наличных денежных средств (банкомата). Проект должен строго следовать принципам SOLID и демонстрировать 
расширяемость архитектуры без изменения существующего кода (Open-Closed Principle).
### 2. Терминология и доменная модель
* Номинал (Denomination): Фиксированное достоинство денежной купюры (например: 100, 500, 1000, 5000 единиц).
* Банкнота (Banknote): Неделимая сущность, обладающая определенным Номиналом.
#### Для системы является иммутабельной:
 - Кассета / Ячейка (Cassette/Slot): Изолированное хранилище внутри АТМ, предназначенное для работы только с одним 
конкретным номиналом. Имеет физическое ограничение по количеству вмещаемых купюр.
 - Банкомат (ATM): Контроллер высокой цепочки, управляющий набором кассет и
   координирующий процессы приема, выдачи и аудита средств.
### 3. Функциональные требования
#### 3.1. Прием наличных (Deposit)
* Система должна принимать на вход пачку банкнот (коллекцию объектов Banknote или структуру Номинал -> Количество).
* АТМ должен автоматически распределить принятые банкноты по соответствующим кассетам в зависимости от их номинала.
- Расширение от себя: Если в АТМ отсутствует кассета для определенного номинала переданной купюры, или кассета 
переполнена, операция должна быть полностью отклонена (транзакционность: либо принимаем всё, либо ничего), 
возвращая специфичное исключение.
#### 3.2. Выдача наличных (Withdraw)
* Система должна принимать на вход запрос на выдачу определенной суммы (целое число).
* Алгоритм выдачи должен сформировать минимально возможное количество банкнот для выдачи этой суммы, исходя из 
текущего остатка в кассетах.
* Примечание: Оптимизировать алгоритм под сложные математические задачи (задача о рюкзаке) не требуется. 
Достаточно "жадного" алгоритма (выдача начиная с максимального номинала к минимальному).
* При успешном расчете кассеты должны уменьшить баланс своего содержимого.
* Система возвращает структуру с выданными купюрами.
#### 3.3. Аудит баланса (Balance/Report)
* Система должна предоставлять информацию о текущем финансовом состоянии.
* Требуется два уровня детализации:
* 1. Общий баланс: Сумма всех денежных средств во всех кассетах (одним числом).
* 2. Детализированный баланс: Актуальное состояние по каждой ячейке (какой
   номинал и сколько купюр осталось).
#### 4. Нефункциональные требования и ограничения (Критично)
   Категорически запрещено проектировать и реализовывать:
* Компоненты пользовательского интерфейса (UI/CLI/Web/Swing). Взаимодействие с АТМ происходит исключительно через 
Public API (методы классов).
* Сущности: Пользователь (User/Customer), Сессия/Авторизация (Auth), Банковская карта (Card), Банковский счет 
(Account), Валюта (Currency).
* Физические периферийные устройства: Клавиатура, Дисплей, Чековый принтер.
* Код должен быть покрыт Unit-тестами (JUnit 5), демонстрирующими все три базовые операции.
#### 5. Требования к обработке ошибок (Бизнес-исключения)
Система должна явно сигнализировать о невозможности выполнения операции с помощью контролируемых или неконтролируемых 
бизнес-исключений:
* InsufficientFundsException — запрашиваемая сумма превышает общий баланс АТМ.
* AmountCannotBeDispensedException — запрашиваемую сумму невозможно набрать существующим набором номиналов (например, 
запрос на 350, если минимальная купюра в кассетах — 100).
* UnsupportedDenominationException — попытка внести купюру номинала, для которого в АТМ не установлена кассета.
#### 6. Подсказки по реализации в духе SOLID (Архитектурный чек-лист)
* Single Responsibility: Не пиши всю логику в один класс ATM. Класс Cassette должен отвечать только за хранение и 
изменение количества своего номинала. Класс ATM — лишь координирует кассеты. Выделяй стратегию выдачи денег в 
отдельный сервис/компонент, чтобы класс банкомата не отвечал за алгоритмы расчета.
* Open-Closed: Если завтра потребуется изменить алгоритм выдачи денег (например, выдавать не минимальным количеством, 
а "миксовать" крупные и мелкие купюры для удобства клиента), ты должен иметь возможность подложить другую стратегию 
расчета, не меняя код самого ATM.
* Interface Segregation / Dependency Inversion: Банкомат должен зависеть от абстракций (интерфейсов) кассет или 
стратегий, а не от их конкретных реализаций.
- С чего начать реализацию?
- 1. Создай enum Denomination.
- 2. Создай интерфейс/класс Cassette (кассета).
- 3. Создай интерфейс WithdrawStrategy (стратегия расчета выдачи купюр). 
- 4. Создай класс ATM, который принимает в конструктор набор кассет (или инициализирует их) и стратегию выдачи.
